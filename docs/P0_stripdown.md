# P0 —— 剥掉 harness 的场景耦合（实验日志）

> 主线：用户判断「我们还没有测到模型能力的边界」，要求**减少 harness 自己提供的东西**，
> 尤其是与当前场景、当前物体紧耦合的工具参数和配方，回到更自由的模型调用上。
> 纪律：每个阶段跑一次、分析、**提交一次**。

## 0. 什么该剥、什么不该剥（已经踩过两次的坑）

| | 内容 | 处理 |
|---|---|---|
| 该剥 | 场景常量 / 配方：篮口 z=0.115、物体中心须 ≥0.17、滑脱阈值 3.8cm、"距篮子 6cm 内下降会推倒篮子"、"先把它推离篮子" | 删除 |
| 该剥 | 把测量翻译成命令的"下一步建议" | 删除 |
| **不该剥** | **任务语义**：工具选择的语义、任务结构骨架（"找到→抓起→搬到篮上→松开"） | **保留** |
| **不该剥** | 工具结果里的**测量**（坐标、偏差、指宽、实测位移、错误） | **保留** |

P0a 与 P0b 两次把"任务语义"当成场景耦合一起删掉，模型立刻退化（29 轮不打一次 `close`）。
**删得掉的是数字，删不掉的是任务。**

## 1. 阶段与结果

| 阶段 | 做了什么 | 结果 |
|---|---|---|
| P0a | `--prompt-mode {full,plain}`；plain 去掉场景补丁 | 失败；且暴露"靠距离判在爪上"的 bug |
| P0a' | plain 补回工具常识 | 失败：30 轮只 locate/move，0 次 close |
| P0b | 工具结果**只留测量**，删掉全部建议 | 首次抓住（t3 width 0.0230）；仍失败 |
| P0c | plain 补回三步任务骨架 | 抓住 2 次；仍失败（重抓 11 次，罐子被推 38cm） |
| P0c' | `_dispatch` 返回 `kind/note`，让 `_grasped` 生效 | 抓住→掉落 |
| P0d | 告知两条"自伤"事实（重复 close 挤压 / 对自己爪中物体 descend） | 抓住→挤压→掉落；掉落误报 8 次 |
| P0e | 掉落事件后重置 `_grasped`；`descend_to` 补 `kind` | 掉落误报 8→1 |
| P0f | 自伤判定改按**工具名**分派 | 三条提示全部触发；**行为逐位不变** |

**九次 run、九个 commit，一次都没成功。** 每次失败的原因都是 harness 自己的缺陷，
不是模型能力——这一节记录它们，因为这类 bug 会反复出现。

## 2. 逐个 bug（全部实测，不是推断）

1. **"在爪上"靠距离判定** → 指垫停在未接触的罐子上方 5.5cm 也算"夹住"。
   P0a 一场里产生 7 次"快滑脱" + 5 次"掉了"的假警报，模型信了，把篮子推走 30cm。
   → 只有 `close` 的 `holding` 判定才能置 `_grasped`。
2. **`locate` 的"下一步建议"** 在 dz=-5.5cm 时宣称"x 轴已对齐；y 轴已对齐"，
   模型据此花了 12 轮微调 xy，从不下降。**一条悄悄忽略真正出错维度的建议，比没有建议更坏。**
3. **`_dispatch` 不返回 `kind/note`** → `_grasped` 从未变 True → "它目前在夹爪里"从未出现。
4. **重复 `close` 不幂等**：指宽 0.0230 → 0.0206，是在继续挤压，下一次抬升必然掉。
5. **掉落事件后没有重置 `_grasped`** → 静止的罐子只要落在爪子 6cm 内就再次误报，
   P0d 一场报了 **8 次**，而模型其实一次都没重新夹住过。这就是"模型一直在反复找罐子"的成因。
6. **`descend_to` 的自伤提示从未触发**：P0d 补了 `kind` 这个 **key**，
   但 adapter 回显的 **value** 是 `"descend_to"`，而循环判的是 `"descend"`。
   → 两个 run 里该提示 0 次命中，而 t5 恰好正是该情形。

第 6 条是这一类里最贵的：**缺 key 一眼能看出来，值属于另一套词表看不出来**。
代码读起来没问题、测试也能过，只是模型永远收不到那条提示。
现在由 `scripts/probe_tool_wiring.py`（纯静态，不需要 GPU）钉死：
循环不得比较 adapter 的 kind 词表、比较的每个名字必须存在于 `TOOL_SCHEMAS`、
每个工具都必须有 `_dispatch` 分支。负对照已验证（把名字改错 → exit 1）。

## 3. P0f 的结论（本轮最重要的一条）

P0f 三条提示**全部按预期触发**（`你手里已经夹着它` t5、`你上一轮已经夹住它` t6、
`物体掉了` t7），**但整条轨迹与 P0e 逐位相同**（`temperature=0`，确定的）。

> **"提示能到达模型" ≠ "提示能改变模型的行为"。**
> 修好投递路径，不等于修好行为。

所以"往工具结果里加提示"这条路在当前配置下收益为 0，不应再作为修复手段。
真正待查的是**模型为什么掉落后 53 轮一次 `close` 都不做**
（假设：每次 `descend` 都把罐子推走几厘米，于是紧接着的 `locate` 总是显示新的大偏差，
模型一直在"重新对准"而永远到不了 close 那一步）。
独立探针：`scripts/probe_regrasp_after_drop.py`。

## 4. 上下文预算（10GB 显存的硬约束）

| 配置 | token | **analytic** attention 矩阵 ≈ |
|---|---|---|
| full（system+tools+task） | 2815 | 242 MiB |
| plain | 1843 | 104 MiB |
| plain + 4 条历史 + 短结果（P0b） | 2498 | 190 MiB |

⚠️ 上表的"矩阵 ≈"是 `N²×16头×2字节` 的**公式预测**（就是 `llm.py` 打印的那个），
**实测低估 5.3 倍**。实测定律见 [`context_budget.md`](context_budget.md)：
`peak_extra(N) = 256 MiB + 170.7 B × N²`，成因见 [`arch_levers.md`](arch_levers.md)。
下面这段当时的推理方向是对的（开销 ∝ N²），但把成因归给了"sm_75 无融合核"——
现在测清楚了，是 **GQA 挡掉了融合核**，memory-efficient 本身在 sm_75 上可用。

N×N 要**实体化** → **显存 ∝ N²**。
这是 `MAX_HISTORY_MESSAGES = 4`、`HISTORY_IMAGE_KEEP = 1` 的由来，
也是"模型遗忘太快"的直接原因：历史只剩 2 轮对话，跨阶段的因果（t5 下降 → t7 掉落）
根本不在上下文里。
