# 工具面重设计：把 harness 收缩成「可自动化 + 场景无关」的原语

> 起因（2026-10-11，用户）：模型的能力**不一定在数字理解上**——每轮喂一堆浮点坐标、
> 相对位移、夹爪状态，模型不一定判断得清"现在是什么状态、下一步该做什么"；**画面更重要**。
> 所以 harness 必须负责的是**完全可自动化、且跨场景可泛化**的语义原语（例如"夹住"，
> 并由代码自行判断要不要继续加压），最后**只给模型概念上的反馈**；同时**减少对仿真精确量
> （物体坐标 / 深度 / 高度）的依赖**——现在的 `approach` 一次做了太多事，而且强依赖仿真能给出精确信息。

参考实现：[`FBddcz/embodied-jev`](https://github.com/FBddcz/embodied-jev)（Jev 分层 XYZ / 视觉航点）。

## 1. 从 Jev 抄什么

| # | 它的做法（出处） | 对我们的意义 |
|---|---|---|
| 1 | 接触/夹持由**代码判概念**：`finger_contacts`（MuJoCo 接触表，`dist ≤ 0.5mm`）→ `held = 双指都接触 and closed`；`grasp_secured = 接触持续 ≥ 0.16s`；另有 `support_contact` / `forbidden_contact`（`physics.py::contacts`）。原文：*"Closing the gripper does not prove a grasp"*（`incremental.py`） | 与我们 `_grasped` 假阳性的教训**独立收敛到同一结论**：夹持是"接触"这一事实，不是指宽阈值 |
| 2 | `target.kind = pixel \| relative \| world`（`libero_policy.py::resolve_plan`）：模型选**一个可见像素**，代码用 depth + 标定反投影成世界点，再加模型给的 `offset_m` | clearance 由**模型**给，不是 harness 常数；物体坐标不用仿真给 |
| 3 | `annotated_image`：只画 **64px 网格 + 实测 TCP 投影十字准线**，不做任何语义标注 | 让模型能用像素说话，同时不泄露"哪个是目标" |
| 4 | **方向由模型定、幅度由代码定**（`hierarchical.py::assemble_motion`："Scale magnitudes, never replace a model-selected direction"）；动作菜单固定 2/10/40 mm 三档 | 把"算数"从模型身上拿掉，但**不拿走决定权** |
| 5 | **拒绝要带理由，绝不悄悄换动作**：*"程序不会悄悄换一个动作"*；`Candidate.admitted=False` + `rejection=原因` 进下一轮反馈 | 我们现在只有**格式错**的重试通道，物理上不可执行的动作没有通道 |
| 6 | **观测源显式可切换**：`privileged`(真值) / `rgbd`(颜色检测+深度) / `vision`(纯像素)，元数据带 `source`；并有守卫测试 `SensorWorld.__getattr__` → 感知层**读任何仿真真值字段即抛错** | 把"真值泄漏"从暗处搬到明处（我们现在正相反，见 §4） |

**不抄**：它的 `subgoal` 菜单 / `servo_choices` 属于**代码侧阶段选择**，是一条拐杖；我们保留
"任务骨架写在提示词里"（等价、透明、模型可自己改）。

## 2. 划线标准

> 代码负责**物理上可自动化 + 跨场景通用**的部分，只回**概念**；
> 模型负责看、选方向、选目标、判断该不该放手。

| 归属 | 内容 | 标准 |
|---|---|---|
| 代码（不可让渡） | 逆运动学 / 关节伺服、夹爪闭合到接触并按需加压、接触判定、动作合法性、工作空间边界、单位换算、标定反投影 | 换物体、换容器、换场景都一样 |
| 模型（必须留） | 抓什么、放哪里、横移方向、抬多高、现在该不该松手、失败后重试还是换策略 | 这就是能力本身 |
| 需要显式选（开关，而不是"顺便替它定了"） | 幅度（代码分档 or 模型给毫米）、clearance（模型给 or 代码常数）、对准（像素闭环 or 世界坐标单次） | 每一条都要能切 |

## 3. 目标工具面

| 现在 | 目标 | 代码内部做 | 只回给模型（概念） |
|---|---|---|---|
| `approach(name, height_offset_cm)` | **`goto_pixel(camera, u, v, offset_mm[3])`** | 像素→深度→世界→IK/伺服；越界/深度无效→拒绝并给理由 | `arrived / short / blocked / invalid_depth` |
| `gripper(open\|close)` + 指宽浮点 | **`grasp()` / `release()`** | 张开→闭合到接触→**按需继续加压**→保持窗口→滑脱判定；`release` 内部含落定窗口 | `grasped / empty / slipped`、`released / still_carrying` |
| `move(direction, distance_cm)` | `move(delta_mm)` 或 `move(axis, size∈{small,medium,large})` | 单轴闭环、阻塞检测、边界校验 | `moved_mm`、`blocked` |
| `rotate(axis, angle_deg)` | 同上，幅度分档 | 姿态伺服 | 实测角度变化 |
| `observe`（已注销） | **`look(camera)`** + **`state()`** | 渲染/取图；从接触表算概念 | `holding / contacts / support / forbidden` |
| `verify(claim)` | 不变（环境真值） | 环境 `check_success()` | 通过 / 未通过 |

**整张表没有任何工具需要知道"物体叫什么"** —— 名字只进人类可读日志，不用于取坐标。

**反馈分层**（这条是本次设计的关键取舍）：

* 模型看到的文本 = **概念**（枚举 + 少量定性描述）；
* 转写里的 `structured_result.measurement` = **数字**（指宽 mm、接触侧、步数、时间）。
  ⇒ 模型不为数字分心，而**仪器不丢分辨率**（`scripts/audit_release_poses.py` 那类离线审计依赖它）。

## 6. 档 A 的具体设计（本次实现）

### 6.1 概念词表（冻结）

```text
grasp()   → status ∈ { grasped, empty, slipped, rejected }
            grasped  = 两指同时对**同一个**物体有接触，且保持 ≥ HOLD_TICKS
            empty    = 闭合到底（指宽 ≤ EMPTY）且无任何接触
            slipped  = 曾双向接触，保持窗口内接触丢失
release() → status ∈ { released, still_carrying }
            released = 张开到位且落定窗口后**无任何指-物接触**
```

可选的 `measurement`（只进转写）：`contact_sides`、`width_mm`、`hold_ticks`、`settle_ticks`。

### 6.2 接触怎么算（场景无关）

```text
两侧手指 body：robot0_leftfinger / robot0_rightfinger（按名字前缀找，不写死）
物体侧：接触表里与该手指成对的**任意 body**（排除另一侧手指、手臂自身、以及基础/台面 geom）
held = 存在 body b，使 (leftfinger,b) 与 (rightfinger,b) 都在接触表里
```

⇒ 不需要物体名字、不需要物体坐标、不需要指宽阈值，跨场景通用。

### 6.3 内部行为

* `grasp()`：① 先张开到位（消掉"仿真是半闭启动、只捏一下"的假阳性）→ ② 逐步闭合，
  每步查接触，双向接触即停 → ③ **继续命令闭合 RAMP 步**（我们已量到不加压会中途滑脱）
  → ④ 保持窗口（命令 hold，查接触是否持续）→ ⑤ 出概念。
* `release()`：① 张开到位 → ② **落定窗口 N tick**（这是"放手后立刻 `verify` 必然失败"的成因：
  两指还没让开，物体还没落定）→ ③ 查接触 → ④ 出概念。

### 6.4 同时被改掉的东西

* `harness._grasped`：从 `"holding" in note`（字符串）改为 adapter 的 **`held` 概念（接触）**。
* `harness._held_body`：新增，持物身份也来自接触表（`object_body`），`_gate_container` 优先用它；
  旧的"离爪心最近"（真值距离）只作为 legacy 回退。
* `format_state`：改为 `机械爪位置 …；爪上：有物体（两指接触）/ 空`，
  去掉指宽三分类、以及 `爪上：<物体名>（离爪心 X.Xcm）`（名字来自真值坐标，属泄漏）。
* `format_outcome`：`grasp/release` 只回概念句，**不含任何数字**；数字进 `structured_result.measurement`。
* `_structured_outcome`：把概念 `status` 与 `measurement` 并入转写（原先只有 eef/steps，概念会被丢掉）。
* `tool_protocol`：`grasp/release` 登记为 v2 工具；**`gripper` 加入 `UNREGISTERED_TOOLS`**（v2 下模型
  不能回退到旧面）；旧面仍是 v1 的 A/B 路径。
* v2 提示词 + `skills/scene_tools.md`：删掉指宽配方与"先 open"的配方，改为 grasp/release 语义。
* 无 GPU 回归：`scripts/probe_harness_dryrun.py` 增加"概念腿"（脚本化 v2 序列，5 项断言）。

### 6.5 实测（2026-10-11，CPU 仿真，无需 GPU）

`bash scripts/simenv.sh scripts/probe_grasp_concept.py`：

| 场景 | 概念输出 | 说明 |
|---|---|---|
| reset（指宽 20.67mm，接触 0） | 无 | **旧指宽规则会报"半闭（指间有物体）"= 假阳性**；接触判定正确 |
| 空中 `grasp()` | `empty` | |
| 对准后 `grasp()` | `grasped`，双向接触，`object_body=alphabet_soup_1_main` | squeeze 10 tick + hold 10 tick |
| 高空 `release()` | `released`，`cleared_after_ticks=1` | |
| 偏轴 / 闭合指下降后再 grasp | `slipped`（单侧接触）/ `empty` | 旧规则在这两处分别报"闭合（空）"与"半闭" |

**关键一条**：完整流程（release 张开 → approach 对准 → grasp → move +z ×2 → approach(篮,25) → release）
之后，`check_success()` **在 release() 返回后立刻就是 True**（此前 8/8 回合"放手后立刻 verify 必失败"）。
注意它的机制：`contain_region` 的 z 上限是 0.137，所以罐子**还在下落**时环境就可能判成功——
用的是 LIBERO 自己的判据，仪器侧仍应记录"落定后"的状态（探针里记录 0.0554）。

**同时暴露的设计缺口（已解决）**：`grasp()` 内部虽然会先张开，但**下降发生在它之前**，
所以"空手张开"必须有入口。决定：`release()` 兼作"张开/复位"，在工具描述与提示词里写明。
若模型出现用错的情况，下一轮可改名为 `open_pads()`。

**回归**：`python scripts/probe_tool_wiring.py` 全 PASS（8 个 v2 工具都有 dispatch 分支）；
`bash scripts/simenv.sh scripts/probe_harness_dryrun.py` → `PLUMBING OK`（含概念腿 5/5）。

## 7. 待办 / 风险

* **档 A 之外**：`approach` 的替代（档 B）需要先做"像素→世界"误差探针（agentview 在物体处约
  2.70 mm/px，而抓取需要 ~2 mm 对齐 ⇒ 必须"先对准再下降"两段式，或做图像空间伺服）。
* **`grasp()` 的"要不要加紧"**：加压后仍需**滑脱检测**（接触集变化 = 滑脱），这条跨场景通用。
* **概念反馈会掩盖细节**（滑到指间外侧、被口沿卡住）：用 `slip` 事件 + 腕部图像补，**不再加浮点**。
* **拒绝通道**：动作不可执行时要回"拒绝 + 理由 + 你现在能做什么"，不退化成静默重试（§1 第 5 条）。

## 7. 档 B 已完成（2026-10-12）

### 7.1 先测误差预算（`scripts/probe_pixel_grounding.py`，CPU，纯几何）

判据用**256 个网格点打平面**（平面必须回来还是平面），而不是拿少量物体比对——
第一版就是后者，结果手腕相机只看到自己的爪子（单样本），把行序判反了两次。

| 判据 | 结果 |
|---|---|
| 深度缓冲行序 | **row0=bottom（OpenGL）**：桌面平面 MAD **4.7mm（第三人称）/ 0.1mm（腕部）**；反向 526mm / 33.7mm |
| 数学正确性 | 往返 u/v 误差 **0.000px**；平面散布 0.1–4.7mm ⇒ 反投影与标定自洽 |
| 第三人称精度 | **2.96–4.04 mm/px**；±1px=3.6mm、±2px=7.4mm；网格 4px=2.8mm、8px=9.5mm、16px=32mm |
| 腕部（抓取高度，罐子在正下方） | **1.10 mm/px**；±1px=1.1mm；网格 4px=2.0mm、8px=5.0mm |
| 表面 vs 中心 | 可见表面比物体中心近 **+20…+90mm**（篮子 +90mm）⇒ **clearance 必须由模型给** |

⇒ 结论：第三人称只能做粗对准（~1cm），**抓取所需的 ~2mm 必须靠腕部近距离**（或图像闭环）。
所以 `goto_pixel` 做成"像素 + 模型给的 offset"的一次到位原语，**由模型分两段用**。

### 7.2 实现了什么

| 层 | 内容 |

### 7.3 守卫与实测（`probe_harness_dryrun.py` 的"像素腿"，无 LLM，~40s）

7 项断言全 PASS，且 `success=True source=env turns=9`：
工具面里没有 `approach` / `goto_pixel` 多次调用且给概念 / **工具结果与状态行里没有物体名** /
**没有物体坐标** / `approach` 被拒且提示替代 / 任务由像素完成 / **画面确实带网格标注**
（按收到的像素里网格颜色计数验证，不是"代码里画了"）。

这套断言就是**行为版的 sensor-rights 守卫**（Jev 的 `SensorWorld` 是静态版：读禁字段即抛错）。
它当场抓到一个真泄漏：档 A 的接触判定把 `object_body="alphabet_soup_1_main"` 写进了每个工具结果的结构化
JSON 里，而 pixels 模式的全部意义就是"没有物体身份"。

### 7.4 版图的粗糙处（已知）

* pixels 模式下 skill 文件仍以 `approach(<名字>)` 叙述，靠提示词附录里一句"一律读作
  `goto_pixel`"过渡。**下一步**：给 pixels 模式写一份独立 skill（把 `approach` 的段落换成像素流程）。
* `rgbd` 档（颜色/深度检测出物体坐标）**没有做**：它需要一个知道物体颜色/大小的**场景专用检测器**
  ——Jev 自己也写着"换了颜色或形状，需要调整检测器"。现在只做 `truth`/`pixels` 两档。
* 第三人称的 3.7mm/px 决定了"一次到位"不可行；`goto_pixel` 不做自动再观察，由模型自己分两段。
* 尚未用真模型跑过（需要 GPU）。预期的新失败形态：模型读网格读不准、或忘了给 clearance。

## 8. 档 B v2：`goto_pixel` → `aim` + `target`（2026-10-12）

### 8.1 为什么改（实测，不是推测）

| 分辨率 | 模型瞄的像素 vs 罐子真实像素 | 离罐子 | 行为 |
|---|---|---|---|
| 256 | asked (96,128)/(112,160) vs can (65.5,123.3) | **>121mm** | 37 轮里只调 1 次像素，其余 36 轮是盲 `move` |
| 512 | asked (96,288) ×4（四次几乎逐像素相同）vs can (131,247) | **101mm** | 5 次像素 + 19 次 `move`，同样转为盲走 |

⇒ 提高分辨率把"瞄错物体"变成"瞄对物体但偏 10cm"，但**偏置是系统性的**，所以"多试几次会收敛"
不成立；而抓取容差只有 ±2.2cm（实测 2.2cm 仍能夹住、4.6cm 夹空）。差 5 倍。

⇒ 结论：这个模型做**绝对像素命名**就是 ~50px/10cm 级精度。补分辨率补不上。要补的是
**把绝对估计换成相对判断**——这正是 Jev 分层原则里的"方向由模型定、幅度由代码定"。

### 8.2 设计（两个工具，一静一动）

| 工具 | 动作用 | 相机 | 返回 |
|---|---|---|---|
| `aim(camera, u, v)` | **干跑**：把红圈画在指定像素上，不动手、不走物理 tick | agent **或** wrist | 同一张带网格的图 + `marked`/`rejected` + mm/px |
| `target(camera, u, v, offset_mm, max_steps)` | 移到该像素（反投影 + 模型给的 clearance） | 只能 agent | `arrived`/`short`/`blocked`/`rejected` |

* 红圈画在**模型给的那个像素**上，不画在反投影再投影回来的位置（往返实测 0.000px，
  画回去只会掩盖接地误差）。同时图上有**青色十字=夹爪真实投影**，所以"我想去哪"和"我在哪"
  可以在同一张图里比。
* 标记几何：**6px 空心圆环 + 1px 黑描边 + 中心点**（`AIM_MARK_RADIUS_PX`）。第一版提案的
  3×3 实心点在 256px 下只有罐子（~16px 宽）的 1/5，看不出差距；而**要看的不是标记本身，
  是标记与目标的差距**。半径是 CLI/环境变量（`AIM_MARK_PX`），因为它是个实验变量。
* **短动作块**：`max_steps`（1~8，默认 8）限制一次调用最多几个 xy/z 修正步，对应 Jev 的
  `max_motor_steps`。旧实现一次调用最多 80 步（~40cm 行程）——两次真实跑各有 36/19 轮盲走。
  块用尽会回 `truncated`，措辞与 `blocked` 分开（一个是"停下来看看"，一个是"过不去"）。
* **拒绝分成两类**，一刀切开：**物理上不可用**（越界/深度无效）→ 软拒绝，带理由 + 把画面一起
  退回（同一轮就能换点）；**工具用错**（`target` 给 wrist）→ 抛错并给替代写法（腕部只能 `aim`）。
* pixels 模式下**从给模型的那份结果里剥掉世界坐标**（`surface_xyz`/`target_xyz`/`offset_m`/
  `depth_m`/`mark`），转写里全留。`mm_per_px` 故意留给模型：它需要一把尺子把格子换成厘米。

### 8.3 守卫与实测

`probe_harness_dryrun.py` 像素腿（无 LLM）：**13 项全 PASS**，`success=True source=env turns=17`，
其中新增的：`aim` 只标注不动手（用 `eef_start==eef_end` 判）、`aim` 可用腕部而 `target` 不行、
越界像素被拒且有理由、**短动作块有上限（每次 ≤ 8 个修正步）**、不给模型世界坐标键、
**红圈真的出现在返回的画面上**（按 `AIM_MARK_COLOUR` 像素计数，不是"代码里画了"）。

肉眼复核（`scripts/probe_aim_marker.py`，故意瞄偏 30px）：红圈画在 requested 像素上，
落点是旁边的瓶子（仪器独立报告离 `alphabet_soup_1` 16mm、离罐子像素 30px），两张图都
能看出差距——即"仪器计数"与"像素"两处独立证实。

### 8.4 第一版（红圈 6px，无放大图）真模型实测：环起作用了，但精度不够

8 回合跑（`SEED=0`），仪器：`python3 scripts/audit_aim_convergence.py outputs/logs/single_node_server.log`。

| 指标 | 实测 |
|---|---|
| 模型真的在用它吗 | 用了：ep0 是 18 aim / 19 target / 65 move，回合内 `aim → 看红圈 → 修正像素 → 再 aim` 的循环清楚可见 |
| Δ_can（瞄准点到罐子真实 xy 距离） | 29 次像素调用：**min 30mm、中位 47mm**；ep0 从 147mm 收敛到 47mm 后**卡住 12 次重复同一像素** |
| 修正粒度 | 1~2 个细格 = 8~16px = 3~6cm |
| 目标是否识别对 | 会来回改：ep0 前 16 轮把**沙拉酱瓶**当 soup（两者在画面里只隔 32px：罐 65，瓶 98），第 17 轮才改到罐上 |
| 成功 | 0/8（但失败点已从"瞄错 10cm"变成"最后 3~5cm + 盲走"） |

两类失败原因，都可归到具体设计缺陷：

1. **红圈太大**：半径 6px 而罐子半径只有 8px ⇒ 红圈压住罐子边缘时看起来仍然"圈住了"，
   模型因此认为已对准（它的原话："红圈 (56,128) 正好落在蓝罐顶部"，实际离罐心 47mm）。
2. **判读分辨率**：模型在 256px 全画面上只能数 1~2 个细格，而抓取需要 ≤5px。
3. **提示词里的旧配方**：任务骨架写着"悬停后看腕部画面，用 move 分 1~3 小步把目标挪到十字上"，
   于是模型在悬停后用 `move +y 3cm` / `move -z 6cm` 盲走（ep0 65 次 move），而不是 aim+target。

### 8.5 第二版（本提交）：红圈 4px + 放大图 + 配方改写

* `AIM_MARK_RADIUS_PX` 6 → **4**：指针必须明显小于它指的东西，"边缘压住"不能被读成"中心对准"。
* **放大图**（`crop_zoom`，裁 64px 再放大 4 倍 → 256×256）：`aim` 围绕红圈，`target` 围绕夹爪十字。
  1px → 4px，5px 的误差变成 20px，**不再是一道判读题**。它覆盖 ±32px（≈±12cm），
  所以粗对准仍用全画面、细对准用放大图（分工，不是替代）。
* 提示词：给出可判定的判据（"红圈中心在物体内部、四边留边均匀"；罐子只有 16px 宽、
  抓取容差 ±2cm ≈ 5px，所以"压住左边一点"就等于抓不到），并把任务骨架里的
  "腕部 + move 微调"改成"**aim 复核 → 用 target 调 offset 压到抓取高度**"，
  `move` 只留给抬高/搬运/撤离。

测法（下次跑完照这个读）：`Δ_can` 的最小值是否 ≤20mm，以及 `aim` 次数是否从 18 降到 3~6。

### 8.5b 第三版：把"目标长什么样"写进场景事实（2026-10-12）

**为什么**：两轮共 16 次抓取，**0 次**抓到 alphabet soup（误抓沙拉酱瓶、番茄酱罐、黄油盒），
而全流程里**没有任何地方告诉模型目标长什么样**——truth 模式由 `approach(<名字>)` 代劳
（所以 8/8），pixels 模式把它交还给模型，而它只能靠"汤罐一般是红橙标签"这种包装常识猜，
在这个场景里恰好猜错（三个容器外形相近：目标=蓝标签矮罐、番茄酱=绿红标签矮罐、
沙拉酱=深绿瓶）。

**改法**：`skills/scene_tools.md` 新增「物体长什么样」一节（外观由像素逐一核对，不含位置，
因为位置是初始状态相关的）：目标=蓝色标签的矮罐（深色盖、浅色椭圆图案）；
两个最易混的（深绿细长瓶 / 绿红标签矮罐）；以及 milk/butter/cheese 各是什么。
提示词里把"先按外观认出目标"放进任务骨架，并要求 `判定` 里先说明红圈落在哪个物体上。

**实测（8 回合跑，前 1-2 回合）**：识别**修好了**——
- `Δ_can` 最小值从 **221mm → 27mm**（v2 全在瞄别的物体）；
- 模型自己的话："腕部画面左侧是**矮的蓝色标签罐**（带浅色椭圆图案，正是 alphabet soup）"；
- 瞄得准的**比例**从 v1 的 13%、v2 的 17% 升到 **46%（60/131 次 ≤22mm）**。

**但暴露出新的、更硬的失败模式：aim 死循环。** ep0 里 80 轮有 **76 次 aim**（只有 2 次 target、
2 次 release），其中连续 76 次是**同一个像素**；而它的 `现状` 文字从第 27 轮起逐字不变、
且**与事实矛盾**——它写"红圈 (60,138)"时实际请求的是 (58,134)：**它在读自己上一轮的文本，
不是在读新画面**。3 次重复时打出的提示（37 条都带着）被完全忽略。

### 8.5c 第三版的两个针对性修正

| 修正 | 针对的错误 |
|---|---|
| **红圈旁写上自己的坐标**（`95,123`，画在圈下方居中，避免被放大图裁掉）| "我在指哪个像素"不能靠模型的记忆：图上印的数字每轮重画，不会过期 |
| 提示词改成"不必追求完美"：写明**实测容差偏 2.2cm（≈6 像素）仍能夹住、4.6cm 才夹空**，并写明"每次 aim 花一个回合、同一像素重复 aim 没有新信息" | 上一版我写的"5px=抓取容差"把模型推成了完美主义者：它永远达不到四边留边均匀，于是永不动作 |
| 重复调用的提示**带上参数回显**（"参数 u=58, v=134 与上一轮逐字相同"）| 让"重复"这条事实可以核对，而不是要求模型自己发现 |
| `REPEAT_STALL_LIMIT = 12`：连续 12 次完全相同的调用就**结束回合并标注** `stalled_repeat` | 76 轮里 76 次相同调用不该算"策略"，该算卡死。MAXTURNS 是同一把守卫的钝版（80 轮后只说"没成功"），这个更早且说明原因 |

### 8.6 已知粗糙处

* `aim` 的代价是**一个模型回合**（每回合 ~2–6s），所以"调到满意再动手"确实更贵；
  这是拿回合换精度的交易，而旧路子（盲目移动）已经证明换不到。
* 尚未测过"模型能不能看出红圈与目标的差距"——这正是下一个岔路口：若 Δ 不收敛，就不该再
  加像素粒度，而应换成**是非题/候选菜单**（Jev 每轴 `negative|hold|positive`）。
* `zoom=True`（以该像素为中心放大 4× 的裁剪）没有做，留作下一个实验变量。
* skill 文件（`skills/scene_tools.md`）已同步改名，但它是**共享**的，truth 模式也会读到
  `aim`/`target` 的段落（那里这两个工具不存在，靠 tools 列表不广告来兑）。

## 9. raw 模式：工具面只剩 move + gripper + verify（2026-10-12）

用户提议的最后一级阶梯：**不要任何与像素有关的工具，只给移动、开关夹爪、看图**
——"按理说有这两个工具，其实所有任务都能做"。

### 9.1 机械上成立（已证明）

`probe_harness_dryrun.py` 的 **raw 腿**（特权脚本，只用这两个工具驱动）：
工具面正好 `{move, gripper, verify}` / `aim`·`target`·`approach` 各被拒一次 /
夹爪只回概念 / 每轮两张画面 / **raw 画面不带网格** / **`success=True source=env turns=34`**。
⇒ 任务用两个工具确实做得完，用户这个判断在机制上是对的。

实现要点：工具面从"黑名单"改成**按模式白名单**（`tool_protocol.MODE_TOOLS`）——
黑名单下每加一个模式都会静默继承它忘了排除的工具，`gripper` 本来就会这样漏回 `truth`；
`raw` 的画面只画夹爪准线（正运动学的投影=本体感觉），**不画网格**（网格是用来给像素命名的）；
`gripper` 重新启用，但**裁决仍由接触表给出**（档 A 的教训：指宽在 reset 时把空手叫 holding）。

### 9.2 模型做不到，而且"做不到在哪"与 pixels 完全不同

raw 模式 8 回合实测：**0/8**，共 491 次 move + 19 次 gripper，**"夹住了" 0 次**，
离罐心最近 38mm（中位 ~220mm，容差 22mm）。两回合被 `REPEAT_STALL_LIMIT` 提前结束并标注。

它的推理（原文）：

> turn 1："目标蓝色矮罐…约在 **(-0.10, -0.10)** 附近；夹爪在 (-0.152, -0.007)。需 +x 5cm、-y 9cm"
> （罐子真值 y = **-0.240** ⇒ 它把 y 估错了 **14cm**）
> turn 5："目标在 +x 方向约 50px ≈ 6cm"（在用提示词给的 1px≈3~4mm）
> turn 11："腕部图里十字正下方压着一个深色盖罐子的顶部，罐心几乎与十字重合" → `-z 15cm`
> turn 12："十字下方是桌面，罐子不在指间…位置偏了" → `+z 15cm`（z 摆动 19cm）

⇒ **新的墙：视觉→世界坐标的换算由模型自己做，而它做得比像素命名还差**（14cm vs 10cm）。
`aim`/`target` 那条路（相机标定 + 深度反投影，往返 0.000px）正是把这一层从模型手里拿走。
换句话说：**"给不给定位工具"就是这条任务的能力边界本身**。

### 9.3 完整阶梯（每一格都有实测）

| 模式 | 工具面 | 定位由谁负责 | 结果 |
|---|---|---|---|
| `truth` | approach(名字) + move + grasp/release + verify | **harness（仿真真值）** | **8/8** |
| `pixels` | aim/target + move + grasp/release + verify | **代码**（标定+深度接地） | 0/14；墙=相邻物体分割 |
| `raw` | **move + gripper + verify** | **模型自己看图估世界坐标** | **0/8**；墙=px→世界换算（14cm） |

## 10. 档 D：把「距离」从模型手里拿走——move 只有三种粒度（2026-10-12）

### 10.1 为什么是这一步

§9 的结论是：`raw` 模式下模型失败在「视觉→世界距离」的换算上（把 y≈-0.10 说成目标位置，
真值 -0.240，偏 14cm）。那就把这个换算**整条拿走**：模型只选**方向**和**一档大小**，
厘米数由代码填。这正是 Jev 在 `embodied_jev/hierarchical.py::assemble_motion` 里的做法
（`scale magnitudes, never replace a model-selected direction`，他的菜单是 2/10/40mm）。

```
move(direction="+y", size="near")      # 模型说的
move(direction="+y", distance_cm=1.0)  # 代码翻的（sim server 根本不知道有阶梯）
```

三档：`far = 10cm`、`near = 1cm`、`fine = 1mm`（字面量 `10cm`/`1cm`/`1mm` 也认）。
仍然传 `distance_cm` 的调用会被**拒绝**并说明原因——否则它可能偷偷退回那个已证明会错的算术。

### 10.2 机械上三档都真的走得出来（干跑实测，非特权脚本做不到）

| 档 | 名义 | 实测（指令轴） | 说明 |
|---|---|---|---|
| `far` | 10cm | **10.02cm** | 跨台面用；单 tick 上限 5cm，12 ticks 走完 |
| `near` | 1cm | **0.92cm** | 主力档 |
| `fine` | 1mm | **0.10cm** | 每次实际只走 0.6–0.8mm（到达窗口 0.5mm 内就停） |

- **1mm 档可执行**是因为 `action_adapter.move` 的 `arrive_tol = min(MOVE_ARRIVE_TOL_M, 请求/2)`：
  当初 1mm 被 2mm 固定窗口吞掉、跑 0 tick、位移 (0,0,0) 像 "blocked" 那次修的就是这里。
- 量档位要**按指令轴量**：`+x far` 的实测位移是 `(0.1002, 0.0006, -0.0118)`——OSC 会往水平
  动作里耦合约 1.2cm 的 z 漂移，取三分量最大会把 1cm 档量成 1.31cm。
- 下降档位必须**不对称**：上升可以 `far`，下降最多 `near`。实测 `far` 下降一次冲了 9.7cm，
  直接穿过「到罐心 +3cm 才 close」的安全余量。
- 阶梯腿（`probe_harness_dryrun.py::ladder_leg`，12 项断言全 PASS）证明**两工具仍能完成任务**：
  `success=True source=env`，但 **119 回合 vs raw 腿的 37 回合**——1cm 档跨 25cm 要 25 步，
  80 回合预算对阶梯是紧的。

### 10.3 这一轮修掉的两个「仪器撒谎」

1. **停滞守卫误杀前进中的动作**。`REPEAT_STALL_LIMIT=12` 只看参数逐字相同，于是连续 12 次
   `+z near`（每次实测走 8.3–9.3mm，12 次共前进约 10cm）被判定卡死并结束 episode；它同时
   打印的「这期间没有任何动作，测量不会变化」**本身是假的**。现在只在 `moved_m(outcome) < 0.3mm`
   时计数。取数必须同时看 `outcome["raw"]`（adapter 对象）与 `measurement`：`_dispatch` 拷的是
   adapter 的 `measurement`，而普通 `move` 根本不用它，只看那里会永远当成没动。
2. 非阶梯路径的下降请求被格式化成 `"0.0"`（move 只接受 0.1~15）→ 协议拒绝 → 同一非法调用
   重试到回合用尽（实测 27 次重试、整回合报废）。**阶梯下结构上不可能发生**：模型选词、代码填数。

### 10.4 提示词也必须一起换，不能只加附录

`raw` 的配方里写着「**一次只走一小段（1~5cm）**」，而阶梯**表达不了** 1~5cm（只有 1cm 与 10cm）。
留着这句话，模型就用 `far` 去满足「至少覆盖我需要的 4cm」——**实测**：自称「还差 4cm」却发 `far`，
一步过冲 2.46 倍，连续 6 次来回摆（`audit_move_ladder.py` 的「过冲倍数」列）。
所以 `get_system_prompt(..., move_ladder=True)` 走 `raw_prompt()`，把那句话**替换**成
「你自己的像素估计 → 档位」的换算表（25px 以上 `far`；3~25px 用 `near` 连走几步；3px 以下 `fine`），
并写明降档/升档规则。

### 10.5 审计工具（都是新增的）

| 工具 | 回答什么 |
|---|---|
| `scripts/audit_move_ladder.py` | 档位分布、**反转后降档/同档/升档**、**档位 ÷ 它自己声称的像素误差 = 过冲倍数**、最长乒乓、夹爪概念 |
| `scripts/audit_ladder_distance.py` | 每回合**离罐心最近距离**（容差 22mm）——两臂唯一可比的指标 |
| `scripts/probe_init_positions.py` | 各 init_state 的物体真值（转写里只有爪心自己的坐标，物体真值必须探针取） |

### 10.7 墙定位到一位数：像素读得不错，px→cm 的乘法稳定错 11 倍

v3 给模型加了「尺」（每步回显爪心实际移动多少像素 + 此处 1 像素值多少毫米），8 回合仍然 0/8，
而且「自称/真值」中位从 0.38× 变成 **0.25×**（更差）。逐回合比对（ep0，真值来自罐子真坐标）：

| 回合 | 真差 (cm) | 真差 (px) | 它报的像素 | 它报的 cm | 隐含 mm/px |
|---|---|---|---|---|---|
| 10 | 23.5 | 63 | 75 | 2.9 | 0.39 |
| 19 | 19.1 | 52 | 78 | 2.5 | 0.32 |
| 22 | 10.0 | 27 | 55 | 1.9 | 0.35 |
| 24 | 11.4 | 31 | 100 / 140 | 3 / 4.6 | 0.30 |

两件事同时成立：**像素读数偏大 1.2~3.2 倍**（可接受），**px→cm 用了 ~0.32mm/px（真值 3.7）**
——它自己在 t10 写着「75px×**3.8mm**≈28.5mm≈2.9cm」：比例知道，**把 285mm 算成了 28.5mm**。
这一个 mm↔cm 滑移占它距离误差的约 4/5。**给尺没用：它不是不知道比例，是算错。**

⇒ 所以最后一步乘法也交给代码：`move(direction="+y", gap_px=80)`，代码用自标定 mm/px 换算、
在 log 尺度上取最近一档（阈值 0.32/3.2cm，每步误差最多缩 3.16 倍）。模型只做两件它确实做得好的事：
读方向、读像素差。干跑实测 `gap_px=80 → far(10cm)` 端到端通过，脚本全知控制器回合数 119 → **71**。

### 10.6 模型实测：阶梯把「换算」拿掉了，但「大小判断」没有跟着变好（v1，8 回合）

同一任务、同一 SEED/INIT_STATE、同样 `MAXTURNS=80`、同样的 `raw` 工具面，只差距离参数形态：

| 指标（都是转写实测） | `raw` 基线（自由填 cm） | 阶梯 v1（三档） |
|---|---|---|
| 成功 | 0/8 | 0/8 |
| `move` 次数 | 487 | 619 |
| 档位分布 | far 86 / near 399 / fine 2 | far 215 / near 385 / fine 19 |
| 方向反转次数 | 108 | 169 |
| **反转后降档 / 同档 / 升档** | 4 / 99 / 5（92% 同档） | **14 / 146 / 9（86% 同档）** |
| **档位 ÷ 它自称的像素误差（中位）** | 0.05×（严重走小） | **0.49×** |
| 档位 ≥ 自身误差 2 倍 | 1% | 1% |
| 离罐心最近 XY（中位 / 最小） | 238 / **38mm** | 214 / **21mm** |
| 进入 22mm 抓取窗口 | 0/8 | **1/8** |

读数：

* **成功了 0/8 对 0/8，但唯一与抓取相关的量动了一格**：XY 最近从 38mm 到 21mm、首次有
  1 个回合进入 22mm 窗口。**1/8 是单回合，只能算"没有变差"，不能算"变好了"。**
* **反转后仍然不降档**（86% 同档），而提示词明写「走过头就降一档」——**用户当初的假设
  （过度偏离后会用更低一档）在这份数据里不成立**。升/降档不是被阶梯"启发"出来的。
* 一个反例说明它**会**说对、只是不稳定：ep7 t76 自己的话是"目标在 +x 方向约 4~5cm，
  `far` 会越过，用 `near` 逐步"——同一回合的 t68–t74 却是在 +y/-y 之间连续 7 次乒乓。
* 结论：阶梯把**单位换算**从模型手里拿走了（过冲中位从 0.05× 变成 0.49×，即它的步子终于
  和它自己说的误差同量级），但**"这一步该多大"仍然是它在猜**。剩下的墙是**停止/收敛规则**，
  不是算术。
## 11. 上下文压缩：每 32 轮由模型自己写一段「我做过什么 / 卡在哪 / 下一步」（2026-10-12）

原来的 `compact_history` 是**硬删**最旧的消息，只留 system + 任务 + 最新 N−3 条，插一句
「更早的 N 条消息已省略」。episode 学到的东西（试过什么、哪里失败、走了多远）全没了，
于是在罐子附近绕了 40 轮的 episode 会从头再绕一遍——四臂 24+8 回合的实测正是这种
**撞回合上限而不是收敛**的形态，而这恰好是「让模型自己回答我卡住了吗、为什么」要抓的东西。

**机制**（`harness.py`，提交 `068fc5e`）

- `summary_due(turn, every)`：触发点是**每块结束后的第一轮**（33 / 65 / 97…）。抽成函数，
  因为压缩与机械上限跑在同一份消息列表上，差一轮就是摘要晚一轮写、或者边界写两次。
- `Harness._summarise_context()`：用 `tools=None` **单独发一次请求**（引擎不会回工具调用），
  让它看到**与正常轮次相同的视图**（同图片预算——压缩的必须是它真拿到的东西，不是另剪一份）；
  回答里混进的工具调用 XML 会被剥掉（用带名字的标签正则，避免把「爪心 < 0.22 且物体 > 0.15」
  这类数学比较一起吃掉）。
- 替换后历史 = **[system, 任务消息, 自述摘要]**，只有这三条；图片也在这里被回收。
- **失败永不杀 episode**：模型报错 / 空回复 / 纯工具调用 → 原历史**原样保留**，
  机械上限继续兜底。
- **一致性**：压缩开启且未显式指定窗口时，`history_messages` 自动放大到 ≥ 一整块
  （32→72）。否则摘要的输入被截断，而它的提示词却写着「到目前为止」——
  **静默错误的摘要比没有摘要更糟**。

**请求文本**（用户给的三问，逐条）：

```
1. 目前为止都做了什么？
2. 当前是否卡住 / 陷入无法收敛的状态？原因是什么？
3. 接下来要做什么？（具体到世界轴、大约多少距离）
```

- 开关：`--summary-every N`（默认 32）/ 运行脚本 `SUMMARY_EVERY=0|N`；`0` = 对照组。
- 转写里记 `context_summary` + `messages_before` + `messages_after`，便于事后看它每次
  给自己写了什么、有没有承认「我在来回摆」。
- 静态检查（无 GPU 无仿真）：`python scripts/probe_tool_wiring.py` 新增 11 项，
  覆盖触发点算术、请求文本、压缩结果形状、`tools=None`、失败保留原历史、XML 剥离、窗口一致性。

### 11.1 首轮实测（look + M2，8 回合；对照 = look 不做压缩）

`OBS_MODE=look SUMMARY_EVERY=32 HISTORY_MESSAGES=200`，其余与 look 臂逐字相同。压缩按设计
在**第 33 / 65 轮各触发一次**（7 个有效回合共 14 次，摘要 526~653 字）。

| 指标 | look（无压缩，4 回合） | **look + M2（7 回合）** |
|---|---|---|
| 离罐心最近 XY（中位 / 最小） | 137 / 80mm | **62 / 4mm** |
| 进入 22mm 抓取窗口 | 0/4 | **2/7** |
| `gripper close` 尝试次数 | 3 | **27** |
| 实际夹住 | 0 | **1** |
| 接近阶段方向正确率 | 56% | 52% |

读数：

1. **机制本身完全按设计工作**：14 次压缩、次次替换成功，模型的自述**诊断是准确的**——
   「在 y 轴上反复越过目标再回退（−y 30cm 后 +y 10cm，又 −y 11cm），因为全局画面里十字经常
   出画，我按像素估距时把『十字在画面左缘』当成了接近，实际已越过」；「曾把腕部图方位读反」。
   14 次里 11 次明确写出「卡住/来回/反复/越过」。
2. **行为跟着变了**：close 尝试 3 → 27 次（不再只是徘徊不动手），并首次真正夹住。
3. **方向正确率没有变**（52% vs 56%）：压缩不修"指哪边"，只修"还记不记得自己要干什么"。
4. **墙移动了**（新一轮的失败原因，按合手那一瞬间的实测 eef z）：

| 罐心 z=0.0384、罐顶≈0.081（干跑成功抓取时 eef z=0.0614） | 结果 |
|---|---|
| 在 z=0.083~0.165 合手（≥ 罐顶） | 夹空 / 接触不稳——两指碰到的是盖沿 |
| 在 z=0.051~0.054 合手但 XY 还差 62mm | 夹空——在罐子旁边合手 |
| **XY 13mm 且 z=0.077 合手** | **夹住了**（全臂唯一一次） |

   即现在的约束是「**XY ≤22mm 且合手高度低于罐顶**」两件事同时满足；模型靠"降到降不动了就
   停"这条规则会在**碰到罐顶**时停下并合手（比成功高度高 2~5cm）。

## 12. 档 E：planner/executor 分层（2026-10-12，提交 `a205f79`）

主模型**没有动作工具**（只有 `look` / `dispatch` / `verify`）；粗粒度阶段由它自主拆分，
每个阶段 `dispatch(task, budget_turns)` 派给**执行者 = look 模式的模型本体**——同一份权重、
不同上下文（它看不到主模型的对话，只看到 task + 现场状态）、自己的轮数预算（用完自动返回）。
主模型读报告验收：成功→下一阶段；失败→把原因写进新的 task 重试。

| 件 | 实现 |

`skills/scene_tools.md` 里的**真值罐心坐标**转写进了任务文本（本轮已剥除，见 §13.3
待办④）——即那 1/4 的成绩里，水平精度是**靠泄漏拐杖**拿到的。

对照能力地板探针：单任务"只对准、给 1cm 判据、不限 look"能到 **0.3~3.3mm**（high 档）。
差别正是：探针任务只有一个目标且被反复用 agent 图核对；而本轮的 75 轮复合任务把
look 限到 2~3 次，模型在**没有可核对判据**的情况下"宣布对齐"。

**下一步（按性价比）**
1. **给执行者像素级对准读数，而不是世界坐标**：agent 图里"十字 vs 罐心"的像素偏差
   （`target`/`aim` 已有 pixel grounding 能力）——是像素测量、不是场景真值，正好补上
   它缺的那个判据，且不违反"无真值模式"的前提。
2. **去掉 planner 提示词里的 look 上限建议**（它把唯一有效的纠错通道关掉了）；
   改成"合手前必须用 agent 图确认十字压在罐上"。
3. 重试退款虽生效，但 259 次截断仍烧掉 ~60min GPU 墙钟 → 降低每轮输出（例如
   thinking 档位 low/medium 或缩短三段格式）比加预算更划算。
